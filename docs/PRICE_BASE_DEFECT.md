# 금액 기준 결함 — `basic_price` 에 두 가지 기준이 섞여 있다

> 발견: 2026-08-03 (모의투찰 5-arm 백테스트 화면에서 active 무효율이 50% 로 나온 것을 추적)
> 상태: **1층·3층 조치 완료 / 2층(근본 수정) 미착수 — 아래 §4 가 그 사양이다**

---

## 1. 무엇이 잘못됐나

`Notice.basic_price` 와 `OpeningResult.basic_price` 는 조달청 API 의 `presmptPrce` 를
그대로 담는다. 그런데 이 값은 **추정가격(부가세 제외)**이고, 우리가 기초금액으로
쓰고 있다. 실제 기초금액은 부가세 포함분이라 **약 1.1 배** 크다.

반면 정적 개찰 파일(`backend/data/opening_results_*.json`)의 `basic_price` 는
**기초금액(부가세 포함)** 이다. 그래서 같은 컬럼에 두 기준이 섞였다.

## 2. 증거 (2026-08-03 운영 실측)

**① 개찰 DB 행 97건 중 93건이 `예정가격 ÷ basic_price ≈ 1.10`**, 중앙값 정확히 110.00%.

```
basic 29,025,455 × 1.1 = 31,928,000   ← 저장된 예정가격과 일치
basic 30,972,728 × 1.1 = 34,070,000   ← 일치
```

예정가격은 **기초금액 ±3%** 의 복수예비가격에서 뽑히므로 사정률이 구조적으로
0.97~1.03 을 벗어날 수 없다. 1.10 이 나온다는 것은 분모가 기초금액이 아니라는 뜻이다.

**② 정적 파일은 올바른 기준** — 4,854건 실측 사정률 0.978~1.022 (중앙 0.9987).

**③ 공고 쪽도 동일** — `R26BK01655168` 의 `basic_price = 673,763,636`,
같은 공고에 `741,140,000` 이 함께 있고 `673,763,636 × 1.1 = 741,140,000`.

## 3. 피해

| 대상 | 영향 |
|---|---|
| 5-arm 백테스트 "전체" 열 | DB 병합분 무효율 **99.8%** → active 가 50.02% 로 보임 |
| 자가보정 (`autocalibrate`, 매주 月 04:00) | 오염된 레코드로 전략 재학습 |
| 모의투찰 등록가 | 기준이 9% 낮아 채점 시 대량 무효 예상 |
| 🔴 **실사용자** | 공고 상세·계산기의 기초금액이 추정가격 → **낙찰하한선이 약 9% 낮게** 계산됨. "안전"으로 표시된 투찰가가 실제로는 무효일 수 있다 |

마지막 항목이 가장 무겁다. "잃지 않게 지켜주는 입찰 안전 비서"라는 포지션과 정면 충돌한다.

## 4. 조치

### 1층 — 집계 가드 (완료)

`arm_backtest.base_is_consistent()` — 사정률이 `0.94~1.06` 밖이면 집계에서 제외.
밴드는 관측 범위(0.978~1.022)의 약 2배로 잡되 1.10 은 확실히 배제되게 했다.

**제외 건수는 응답(`n_excluded_base_mismatch`)과 화면에 반드시 표기한다** —
조용히 잘라내면 화면이 "전수를 봤다"로 읽히는데 사실이 아니다.

부수적으로 "전체" 열이 낙찰하한 체계가 다른 입찰방법을 뭉갠다는 문제도 함께
처리했다: 방법별 무효율 표(`by_method`, 표본 30건 이상)를 추가하고 경고를 붙였다.

### 3층 — 하한율 단일 소스 (완료)

`dataset._load_db_records` 가 `lower_limit_rate=87.745` 를 상수로 박고 있었다.
2026-01-30 요율 개정(10억 미만 공사 89.745%) 이후로는 틀린 값이다.
→ `lower_limits.get_lower_limit_rate(금액, 공고일)` 로 교체.

### 2층 — API 실측 (2026-08-03 완료)

운영 컨테이너에서 실호출한 결과, **기초금액은 이미 API 에 있었다.**

**개찰 API** (`getDataSetOpnStdScsbidInfo`, 38필드) — 크롤러가 쓰던 바로 그 응답:

| 필드 | 값(샘플) | 의미 |
|---|---|---|
| `presmptPrce` | 55,390,182 | 추정가격 — 우리가 잘못 읽던 값 |
| **`bssAmt`** | **60,929,200** | **기초금액** |
| `rsrvtnPrce` | 60,990,925 | 예정가격 |
| `sucsfLwstlmtRt` | 89.745 | 낙찰하한율 (레코드별 제공) |

2,000건 실측: `bssAmt` 1,998건(99.9%) 제공, 정정 후 사정률 0.9896~1.0050 —
**전량이 허용 범위 안**. `sucsfLwstlmtRt` 도 1,998건 제공.

**공고 쪽**은 목록 API(143필드)에 기초금액이 없고, 전용 오퍼레이션
`getBidPblancListInfoCnstwkBsisAmount` 에 `bssamt` 로 있다. 여기엔 **A값
구성요소도 함께** 온다(`npnInsrprm`·`mrfnHealthInsrprm`·`odsnLngtrmrcprInsrprm`·
`rtrfundNon`·`sftyMngcst`·`qltyMngcst`·`envCnsrvcst` 등 + `bidPrceCalclAYn`).

커버리지 실측(모의투찰 등록 272건 대조):

| | |
|---|---|
| 기초금액 확인 | 218건 (80.1%) — 조회 창 21→50일로 넓혀도 동일(구조적 부재) |
| 등록 시점에 이미 공개 | 206건 (**실효 75.7%**) |
| 소액수의견적 / 적격심사제 | 90.8% / 83.1% |
| 최저가낙찰제 / 제한적최저가 | 25.0% / 8.3% |
| A값 산정 대상 | 212/218 (97.2%), 기초금액 대비 1.8~4.5% |

⛔ **폴백 후보는 둘 다 탈락했다**
- `× 1.1` 하드코딩: 218건 중 **2건은 비율이 1.0000** (두 값이 같다)
- 배정예산(`bdgtAmt`): 152/218 만 일치, **61건이 벗어나고 최대 9.69배**

→ 신뢰할 수 있는 소스는 기초금액 API 하나뿐이다. 남는 20~25% 는 추정해서
채우지 말고 **"기초금액 미확인"으로 표시**해야 한다. 잘못된 기초금액으로 낸
"안전" 판정이 바로 지금의 사고다.

### 2층-A — 개찰 크롤러 정정 (2026-08-03 완료)

- `basic_price` 를 `bssAmt` 에서 읽는다. **`bssAmt` 가 없으면 행을 버린다**
  (추정가격으로 대체하면 기준이 다시 섞인다)
- `OpeningResult.lower_limit_rate` 신설(마이그 `c2f7a5e91d80`) — `sucsfLwstlmtRt`
  저장. `_load_db_records` 는 이 값을 먼저 쓰고 없을 때만 금액대 테이블로 폴백
- `winner_rate` 폴백 기준을 예정가격으로 통일(API·정적 파일과 일치)
- 기존 행 백필: `backend/scripts/backfill_opening_basis.py` (멱등, API 재조회)
