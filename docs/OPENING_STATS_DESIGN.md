# 누적 개찰 통계 (opening_stats) — 설계 정본

> 최종 갱신: 2026-08-08 (S1 구현)
> 관련: `docs/PRICE_BASE_DEFECT.md`(기초금액 기준 사고) · `docs/COMPETITIVE_STRATEGY.md`(안전망 4레이어) · `docs/BENCHMARK_WIN_REACH.md`(예측 금지 근거)

---

## 0. 왜 하나

경쟁 3사(디마툴즈·지투비플러스·비드프로) 어디도 **누적 개찰 통계를 사용자에게 돌려주지 않는다.**
우리는 이미 재료를 갖고 있다 — `opening_results` 원장이 매일 쌓인다. 안 쓰는 게 이상한 상태였다.

사용자가 실제로 묻는 건 한 줄이다.

> "이 기관, 이 방식, 이 금액대면 **보통 몇 %에서 낙찰되나?**"

이건 예측이 아니라 **과거 사실 진술**이다. 우리 포지션(낙찰가 예측 안 함)과 정면으로 어긋나지 않는
유일한 형태의 "숫자 도움"이라서 여기를 고른 것이다.

---

## 1. 비목표 (먼저 못 박는다)

이 기능이 **하지 않는 것**:

1. **낙찰가·사정률 예측 금지.** 사정률은 복수예비가격 추첨이라 과거 분포가 다음 회차를 예측하지 않는다.
   표기는 언제나 "지난 1년 실제로 이랬습니다" 사실 진술이어야 한다.
2. **'낙찰률' 이라는 말을 쓰지 않는다.** 여기 `winner_rate_*` 는 낙찰자의 **투찰률**(낙찰가÷기초금액)이지
   이길 확률이 아니다. 두 뜻이 섞이면 "낙찰률 90%" 같은 거짓 지표가 만들어진다
   (CLAUDE.md 함정 2 · 블로그 K5 에서 실제로 잡힌 오용).
3. **업체별 투찰 이력은 다루지 않는다.** 참가자 원장(`opening_participants`)은 등록 공고만 담고 있고,
   전수 수집은 하루 169k행이라 함정이다. 개인정보·경쟁사 추적 성격도 있어 별도 판단이 필요하다.
4. **표본이 모자라면 아무것도 보여주지 않는다.** n < 10 은 셀 자체를 만들지 않는다(§3).

## 2. 착수 전 실측 (2026-08-07, 운영 DB 4,984행 / 2026-05-18 ~ 08-06)

설계를 **세 군데** 바꾼 측정이다.

| 항목 | 실측 | 설계에 미친 영향 |
|---|---|---|
| 사정률 산출 가능 행 | 4,944 / 4,984 (**99.2%**) | 추가 API 호출 없이 집계가 된다 → S1 착수 가능 |
| 사정률 검사 통과 | 4,225 (84.8%) | 나머지는 미정정 원장(추정가격 기준). 제외하고 **센다** |
| **참여사수 보유** | **0 / 4,984 (0%)** | 🔴 크롤러가 `None` 을 박아 놓고 아무도 안 채웠다 → **S1 에 포함** |
| 낙찰하한율 보유 | 452 (9.1%, 08-03~) | 필드 추가 시점 이후만. 시간이 채운다 |
| `region` 보유 | **0%** | 🔴 개찰 API 미제공 → **지역을 축에서 뺀다** |
| 기관×방법 셀 n>=10 | 94 / 1,393 (행의 40.1%) | 🔴 기관 축은 성기다 → **기관 무관 셀을 항상 함께** 만든다 |
| 참가자 원장 | 287,532행 / 1,124 공고 (공고당 평균 **256개사**) | 경쟁 강도가 콘텐츠가 된다 |

### 2-1. 사정률 평균은 신호가 없다

기관별 평균 사정률 실측: 밀양시 99.840% · 군산시 99.920% · 청주시 99.901% · 안동시 99.979% ·
여수시 99.997% · 수원교육지원청 100.052%. **전부 100% ±0.16%p 안**이다.

예정가격이 기초금액 주변 추첨이니 당연한 결과다. 그래서 **평균은 저장하지 않는다.**
저장해 두면 언젠가 화면이 "이 기관 사정률은 99.84%" 로 읽고, 그건 예측처럼 보인다.
의미가 있는 건 **분포의 폭**뿐이다.

### 2-2. 낙찰 투찰률은 신호가 있다

| 입찰방법 | n | 평균 | 범위 |
|---|---|---|---|
| 소액수의견적 | 3,792 | 90.28% | 88.24 ~ 100.00% |
| 적격심사제 | 338 | 90.14% | 88.08 ~ 93.43% |
| **최저가낙찰제** | 50 | **69.74%** | 51.35 ~ 99.66% |
| 수의시담 | 17 | 97.95% | 88.52 ~ 105.99% |

방식이 바뀌면 게임이 통째로 바뀐다. 이건 사용자에게 실제로 쓸모가 있다.

### 2-3. ⚠️ 아직 판정하지 않은 것 — 예비가격 범위 ±2% vs ±3%

관측 사정률 편차: p50 0.509% · p90 1.234% · p99 **2.017%** · |편차|≤2.0% 가 **98.9%**.

`simulation_service` 는 ±3% 균등을 하드코딩하는데 관측은 훨씬 좁다. 다만 **이것만으로
±2% 운용이라 단정할 수 없다** — 예정가격은 예비가격 15개 중 4개의 *평균*이라 중심극한으로
저절로 좁아진다(±3% 균등이어도 σ≈0.87%). 기관별 최대편차로 분류하면 **표본 크기에 속는다**
(n=25 면 최대편차가 작게 나오는 게 당연하다).

→ **S1 은 분포를 저장만 하고 ±2%/±3% 판정을 하지 않는다.** 표본이 쌓인 뒤 별도로 검정한다.
이건 "지표가 상식을 벗어나면 데이터의 기준을 먼저 의심한다"(함정 22)의 같은 계열이다.

## 3. 표 구조

`opening_stats` — 한 행 = 한 축 조합. 모델 정의·근거는 `models.OpeningStat`.

**축**: `organization` × `bid_method` × `amount_band`

- 기관 무관 집계는 `organization = ''` (빈 문자열). **NULL 이 아니다** — Postgres 는 UNIQUE 에서
  NULL 을 서로 다른 값으로 보므로 NULL 을 쓰면 중복 행이 조용히 쌓인다.
- `amount_band` 경계는 `lower_limits.AMOUNT_BANDS` **한 곳**에서만 정의한다. 하한율이 바뀌는
  지점이 곧 게임이 바뀌는 지점이고, 경계를 통계 쪽에 따로 적으면 요율 개정 때 두 소스가 갈라진다.
- 지역은 축이 아니다(§2 — API 미제공).

**담는 값**: 분위수만. `winner_rate_p10/p50/p90` · `reserved_ratio_p10/p50/p90` ·
`participants_p50/max/n` · `n` · `period_start/end`.

**기간**: 최근 365일 창. 월 버킷으로 쪼개지 않는다 — **분위수는 부분 집계를 합칠 수 없어서**
월별 p50 을 모아도 전체 p50 을 못 만든다. 대신 매일 전량 재계산한다(연 2~4만 행이라 몇 초).

**최소 표본** `MIN_SAMPLE = 10`. 미달 셀은 **저장하지 않는다** — 저장해 두면 결국 누군가 쓴다.
`arm_backtest.MIN_METHOD_N`(=30)보다 낮은 건 목적이 달라서다: 저기는 arm 끼리 **차이**를
주장하고, 여기는 분포를 **있는 그대로** 보여줄 뿐이다.

## 4. 파이프라인

```
19:00  verification.daily_crawl_opening_results   개찰 원장 적재 (+참여사수 카운트)
19:30  opening_stats.rebuild                       전량 재집계 → opening_stats
```

재집계는 원장이 소스라 **언제 돌려도 안전**하다. 19:00 이 실패해도 어제까지의 원장으로 돌아
통계가 통째로 비지 않는다. 어드민 `/admin/system/triggers` 에서 수동 실행 가능.

### 4-1. 참여사수는 공짜다

개찰 API 는 **참가자 한 명당 item 하나**를 준다. 즉 그 공고로 온 행 수가 곧 참여사수다.
`_apply_participant_counts` 가 창 단위로 세어 반영한다 — **추가 API 호출 0**.

⚠️ `_upsert_opening_result` 에 얹을 수 없다. 그쪽은 낙찰가가 이미 있는 행을 건드리지 않는데
(실 결과는 안 바뀐다는 규칙), 그러면 기존 4,984행이 영영 비어 있게 된다.

⚠️ 이 값은 "그 조회 창에서 API 가 준 행 수"다. 창을 다 훑었을 때만 참이며, 페이지 상한에
걸리면 크롤이 `RuntimeError` 로 멈추므로 잘린 채 저장되지는 않는다.

## 5. 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| **S1** | 참여사수 수집 · `opening_stats` 표 · 집계 서비스 · 일일 태스크 | ✅ 2026-08-08 |
| **S2** | 공고 상세에 "이 기관 이 방식은 보통 ○○% 에서 낙찰됐습니다(n=NN, 지난 1년)" 한 줄 | 대기 |
| **S3** | `/agency/{기관}` SEO 페이지 — 색인 표면 확대 | 대기 |
| **S4** | 계산기 힌트 · 예비가격 범위 실측화(§2-3 검정 후) | 대기 |

**S1 이 게이트다.** 화면(S2~)은 셀이 실제로 얼마나 차는지 보고 판단한다 —
지금 기관 셀은 행의 40% 만 덮으므로, S2 를 켜기 전에 "몇 %의 공고에서 통계가 뜨는가"를
먼저 재야 한다. 안 뜨는 화면을 만드는 건 08-06 익스텐션 CTA 에서 이미 한 번 겪었다.
