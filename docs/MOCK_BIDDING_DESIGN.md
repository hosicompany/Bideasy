## 0. 사전 등록 (Pre-registration) — 지표·게이트 동결

**이 섹션은 구현 착수 전에 작성·동결되었다. 결과를 보고 지표나 게이트를 바꾸는 것(체리피킹)을 금지한다.**
`BENCHMARK_WIN_REACH.md` §0 과 같은 규율이다. 그때 이 규율이 있었기에 G1 의 결론을 정직하게 기각할 수 있었다.

### 0.1 이 기능이 백테스트와 다른 단 하나

이미 백테스트(`autocalibrate/optimizer`)도, 일일 사후 검증(`prediction_verifier`)도 있다. 그럼에도 이걸 만드는 이유는 **한 가지**다.

| | 백테스트 / 현 사후 검증 | 모의투찰 |
|---|---|---|
| 가격 결정 시점 | **개찰 후** (검증 시점의 active 전략으로 계산) | **마감 전** |
| 나중에 값이 바뀌나 | **바뀐다** — 자가보정이 매주 파라미터를 갱신하면 "그때 우리가 추천한 값"이 소급 변경됨 | **불변** (append-only) |
| 측정의 성격 | 사후 재구성 | 전향적 실험 |

`prediction_verifier.compute_recommendations(notice)` 는 개찰 후에 호출되고 `_get_active_strategy()` 를 읽는다. 즉 **현재 성능 측정은 자기충족적**이다. 마감 전에 가격을 못 박아야만 "우리 알고리즘이 실제로 얼마나 맞나"를 말할 자격이 생긴다.

### 0.2 지표 정의 (실행 전 동결)

판정 공식은 운영 중인 `optimizer.simulate_params`(optimizer.py:94-98)와 **동일**하다. 모의투찰이 자가보정과 다른 정의를 쓰면 두 시스템이 서로 다른 말을 하게 된다.

- **실제 하한선** = `reserved_price × lower_limit_rate / 100`
  - `lower_limit_rate` 는 **공고 명시값(`Notice.lower_limit_rate`) 우선**, 결측 시 `lower_limits.get_lower_limit_rate(contract_type, basic_price, bid_date)` 폴백. (2026-08-02 크롤러 수복으로 공고가 실측값을 주게 됐다 — 금액대 테이블 추정보다 정확하다.)
- **WIN** = 등록가 ∈ [실제 하한선, 실제 낙찰가]
- **DROPOUT (무효)** = 등록가 < 실제 하한선
- **LOST** = 하한선은 통과했으나 낙찰가 초과
- **NO_RESULT** = 개찰결과 미도착 (채점 보류 — 실패가 아니다)
- **VOID** = 취소공고·유찰 등 판정 대상 아님

**지표 우선순위 — 이 순서를 뒤집지 않는다.**

| 순위 | 지표 | 왜 이 순위인가 |
|---|---|---|
| **1차** | **무효율(dropout)** | 브랜드 KPI 가 유효율이다(전역 규칙 §4-2). 무효는 입찰 자체가 없던 일이 된다 |
| 2차 | 적중률(win) | 자가보정과 동일 정의 |
| 3차 | **실제 등수 분포** | 참가자 데이터가 있어야 산출(§4-3). 승패 이진값으로는 개선 방향이 안 보인다 |
| 4차 | **사정률 예측 오차** `\|reserved/basic − 예측\|` | 개별 승패는 추첨 노이즈가 크지만, 이 오차는 우리 모델의 순수 신호다 |

세그먼트: `bid_method × 금액대(bracket) × 기관 × 지역`.

### 0.3 비교 대상 5 arm (동시 등록)

실제 돈이 나가지 않으므로 arm 을 여러 개 낼 비용이 0 이다. 하나만 기록하면 "다른 선택을 했다면?"을 영영 잃는다.

| arm | 정의 | 근거 |
|---|---|---|
| `standard` | 기초금액 × 97.5% (사정률 −2.5) | 사용자 슬라이더 기본값 — 실사용자 다수의 실제 행동. 과거 win 0.52% |
| `active` | 현 자가보정 active 전략 | 운영 정본 |
| `frontier_c5` | dropout 캡 5% 최적 파라미터 | 벤치마크 §4 "무릎" 하단 |
| `frontier_c10` | dropout 캡 10% 최적 파라미터 | holdout 2025 win 32.1% |
| `aggressive` | 기초금액 × 88.0% (−12) | 경쟁사 추격 가설. 과거 무효 27.6% |

### 0.4 게이트 (실행 전 동결)

**G-A · 파이프라인 건전성** (착수 후 첫 4주)
- 조건: 등록분의 **채점 도달률 ≥ 60%** (등록했는데 개찰결과가 안 붙으면 데이터가 안 쌓인다)
- 미달 시: 지표 해석 금지. 원인(조인 실패·개찰 지연·취소공고)부터 수습한다.

**G-B · 전략 우열 판정** (적격심사제 채점 누적 **≥ 400건** 도달 시)
- 조건: `active` 의 무효율이 `standard` 이하이면서, win 의 Wilson 95% CI **하한**이 `standard` 의 CI 상한을 상회
- 통과 시: "우리 추천이 기본값보다 낫다"를 우리 데이터로 말할 수 있다(대외 표기는 §0.6 준수).
- 400건 기준은 `BENCHMARK_WIN_REACH.md` §5-3 의 G2 재판정 조건과 같은 값 — 그 재판정을 이 데이터로 수행한다.

**G-C · 전략투찰 제품화 판정** (G-B 통과 후)
- 조건: `frontier_c10` 의 win CI 하한이 `active` 의 CI 상한을 상회 **그리고** 무효율 ≤ 11%
- 통과 시: Pro+ "전략 투찰(고위험 고지)" 모드 제품화 **검토** 착수 (제품화 자체는 별도 결정).
- 불통과 시: 현 포지션 유지. 이건 실패가 아니라 "안전 우선이 옳았다"는 답이다.

**킬 기준 (사전 등록 — 사후 합리화 금지)**
- 착수 8주 후에도 G-A 미달이면 **기능을 중단**하고 원인 분석만 남긴다.
- 등록·채점이 도는데 6개월간 어떤 arm 도 `standard` 를 유의하게 이기지 못하면, "알고리즘 우위 주장"을 접고 제품 서사를 안전·유효율로만 좁힌다.

### 0.5 유효성 체크 (구현에 내장, 실패 시 등록 거부)

1. `registered_at < deadline_at` — **위반 시 등록 거부**. 이 가드가 실험 전체의 신뢰 근거다.
2. `(bid_no, arm)` UNIQUE — 재실행이 중복 등록을 만들지 않는다.
3. 채점 시 `mock_bids` 행은 **절대 UPDATE 하지 않는다**. 재채점은 `mock_bid_results` 에 새 행(`scoring_rev`+1).
4. arm `active` 의 등록가는 같은 파라미터로 `recommend_bid_price` 를 다시 부른 값과 일치해야 한다(구현 자체 검증).

### 0.6 대외 표기 금지 사항

- ⛔ **"낙찰률 N%" 마케팅 금지** (전역 규칙 §4-2). 모의투찰 결과를 낙찰률로 홍보하면 규칙 위반이다. 대외 지표는 **유효율(무효 0)** 과 재사용률.
- ⛔ 이건 **counterfactual(반사실) 재구성**이다. "우리가 실제로 넣었어도 같은 결과"라는 보장이 아니다(§10).
- ⛔ 표본이 게이트 미달인 상태의 수치를 근거로 쓰지 않는다.

## 2. 설계 원칙

**P1. 사전 등록이 전부다** — 마감 전 확정, 이후 불변. 전략 버전·코드 리비전과 함께 **그 시점에 우리가 본 입력 스냅샷**을 박는다. 기초금액이 정정(`notice_kind='변경공고'` 실재)되거나 A값이 나중에 백필되면 "그때 본 정보"가 달라지는데, 스냅샷이 없으면 사후 변명이 가능해진다.

**P2. 한 공고에 5 arm 동시 등록** — §0.3.

**P3. 판정 함수는 단일 소스** — `simulate_params` 와 같은 정의를 공유하는 함수 하나로 뽑는다.

**P4. 참가자 데이터는 등록한 공고만 저장** — 공사 개찰은 하루 169k행 규모(census 조사)라 전수 저장은 함정이다. 등록분으로 한정하면 데이터량이 수십분의 1로 떨어지면서 얻을 건 다 얻는다.

**P5. 초기엔 자가보정 루프에 자동 연결하지 않는다** — 설계가 덜 검증된 실험이 운영 전략을 바꾸면 안 된다. G-B 통과 후 수동 승격.

## 3. 등록 대상 선정 규칙 (사전 고정 — 편향 방지)

"좋아 보이는 공고만" 등록하면 지표가 부풀려진다. 규칙을 고정하고, 예외를 두지 않는다.

**포함**: `contract_type='CONSTRUCTION'` · `basic_price > 0` · `end_date` 가 미래 · `bid_method` 가 비어있지 않음

**제외**:
- `notice_kind = '취소공고'` — 실재한다(정찰에서 발견). 취소된 공고에 투찰할 수는 없다.
- `bid_method` 가 전략 미정의(`협상에의한계약` 등 가격경쟁이 아닌 방식)
- 이미 `(bid_no, arm)` 등록된 건

⚠️ 제외 규칙을 나중에 추가하면 그 시점 이전/이후 데이터가 섞인다. 바꿔야 한다면 **버전을 올리고 분석에서 분리**한다.

### 4-3. `opening_participants` — 정답지 확장

```
bid_no, rank, company, bid_price, bid_rate, sucsf_yn
```

지금 `opening_result_crawler._parse_item_to_kwargs` 는 참가자 행을 `return None` 으로 **버린다**(낙찰자만 저장). API 는 전원의 `bidprcAmt`·`opengRank` 를 주고 있다. 이걸 주우면 판정이 이렇게 달라진다:

| 지금 | 참가자 저장 후 |
|---|---|
| WIN/LOST/DROPOUT 3분류 | **실제 몇 등이었는지** |
| "졌다" | "**2위, 낙찰가와 0.003%p 차이**" |
| 경쟁 강도 모름 | 참여자 수 실측 → 참여자 예측 모델 검증 |

```
매시   mock_bid.register          ★신규 — 마감 2h 전 이내 & 미등록 공고를 arm 별 등록
19:00  verification.daily_crawl_opening_results  (기존 · 참가자 저장으로 확장)
20:30  mock_bid.score             ★신규 — 개찰결과 도착분 채점
月 21:00 mock_bid.weekly_report   ★신규 — 게이트·표본품질·큐·오답노트 성적표
```

**왜 02:00 재조회가 필요한가**: 정기 크롤(19:00)은 개찰일 기준 **2일 창**만 본다.
그런데 개찰은 마감 당일에 나도 **낙찰자 확정(적격심사)은 며칠~수주** 걸리고,
크롤러는 낙찰자 행만 `OpeningResult` 로 저장한다. 그래서 2일 안에 확정되지 않은
공고는 **영영 결과가 안 붙어** 채점 도달률이 33.8% 에서 멈췄다(§9 · 2026-08-13).

**왜 매시인가**: 마감시각이 공고마다 다르다. 하루 1회로는 "마감 전 등록"을 보장할 수 없다. 등록 태스크는 `registered_at < deadline_at` 을 코드로 강제하고, 위반 시 그 건을 **거부**한다(§0.5-1).

## 7. 함정·금지 (구현 시 준수)

1. **`mock_bids` 를 UPDATE 하지 말 것** — 사전 등록의 의미가 사라진다. 재채점은 결과 테이블에 새 행.
2. **낙찰률 대외 표기 금지** — §0.6.
3. **등록 대상 규칙을 조용히 바꾸지 말 것** — §3.
4. **판정 정의를 `simulate_params` 와 갈라놓지 말 것** — 갈라지면 자가보정과 모의투찰이 다른 말을 한다.
5. **참가자 전수 저장 금지** — 등록분만(§P4).
6. **자가보정 자동 연결 금지** — G-B 통과 전까지(§P5).
7. **취소공고를 등록하지 말 것** — `notice_kind` 로 걸러진다.
8. **등수는 유효 투찰만 센다** — 개찰 API 는 낙찰하한선 이상에만 `opengRank` 를 준다
   (운영 표본의 47.6% 가 무효 = 순위 없음). 무효까지 세면 개찰조서와 다른 축이 되고,
   실제로 등수가 평균 15.79 부풀어 있었다(§9 · 2026-08-11). `estimate_rank` 에는 반드시
   `_valid_participant_prices` 로 거른 목록만 넘긴다. `sucsf_yn` 으로 거르지 말 것 —
   그건 '낙찰자인가'라 1명만 남는다. 축이 다시 갈라지는지는 `rank_axis_health` 가 감시한다.
9. **우리가 무효(DROPOUT)면 등수를 만들지 말 것** — 8번을 우리 자신에게도 적용한다.
   유효 투찰은 전부 하한선 이상이고 DROPOUT 은 그 미만이라, 등수를 매기면 **정의상 항상
   1위**가 되어 무효를 많이 내는 arm 일수록 성적이 좋아 보인다(§0.2 1차 지표와 정반대).
   단 **참가자 수는 무효 건에도 갱신한다** — "유효 투찰이 몇 건이었나"는 그 공고의
   성질이지 우리 판정의 성질이 아니다. 무효를 백필 후보에서 빼면 참가자 수가 부분 응답
   시점에 영구히 동결된다(실제로 한 번 그렇게 만들었다가 리뷰에서 잡혔다).
10. **등수 분포를 arm 간 비교에 쓸 때는 무효율과 함께 볼 것** — 무효를 빼면 "유효였을
   때"로 **조건부인** 분포가 된다. 공격적 arm 은 하한선이 예상보다 낮게 나온 공고에서만
   유효가 되고 그때는 최저가라 1위다. 제외 수는 `rank_distribution_excluded` 가
   **사유별로**(`dropout` / `no_rank_data`) 돌려준다 — `summarize` 가 제외 수를 함께
   주는 것과 같은 이유다(숨기면 전수로 읽힌다). 무효만 세면 양방향으로 틀린다:
   참가자 데이터가 없어 애초에 후보가 아니던 건을 세면 과대, 유효 판정인데 등수를
   못 구한 건을 빠뜨리면 과소다.
11. **축 감시(`rank_axis_health`)의 판정 하한은 공고 수다** — 결측률은 공고 단위로
   흔들리고(공고 하나가 통째로 유효일 수 있다) 운영은 공고당 참가자가 ~250행이라,
   행 기준만 두면 **공고 1건으로도 하한을 넘겨** 가드가 무력해진다. 표본 미달이면
   `healthy=None`(판정 보류)이고, 화면은 이 상태도 **경고로 보여야 한다** — 감시
   불능을 조용히 넘기면 정상과 화면이 같아져서, 이 장치를 만든 이유가 사라진다.
12. **개찰 시각과 낙찰자 확정 시각은 다른 축이다** — 개찰은 마감 당일에 난다
   (실측 786공고 지연 0.0일). 늦는 건 **적격심사**이고 며칠~수주 걸린다.
   `OpeningResult` 는 낙찰자 행에서만 만들어지므로, "개찰일 기준 창"으로 크롤하면
   그 창 안에 확정되지 않은 공고는 **영영 결과가 안 붙는다**. 창을 넓히는 것으로
   때우지 말 것 — 정기 크롤은 2일로 두고 **채점 대기분의 개찰일만 표적 재조회**
   한다(§5 · 02:00). 그냥 `days_back` 을 늘리면 매일 전체를 다시 훑게 된다.
13. **개찰 API 는 날짜 창 조회만 지원한다** — `bidNtceNo` 단독은 "필수값 입력
   에러"이고 날짜와 **같이 줘도 무시된다**(2026-08-13 실측: total 이 날짜창만 준
   것과 동일). 특정 공고를 다시 보려면 그 개찰일을 통째로 훑는 수밖에 없다.
   하루 분량은 84~170페이지로 **날에 따라 2배 이상 흔들리므로**(08-05 실측 vs
   레포 정본 169k행) 상한·소요를 가늠할 때는 큰 쪽을 기준으로 본다.
14. **API 의 날짜 파라미터는 KST 표기, 운영 컨테이너는 UTC** — `datetime.now()` 를
   그대로 포맷해 보내면 9시간 과거를 요청한다. 개찰 크롤 계열에서는 `_now_kst()`
   를 쓸 것. 이 실수로 19:00 크롤이 "10:00 까지"를 요청해 당일 개찰분이 하루씩
   밀려 왔다(§9 · 2026-08-13).

### 원인과 2026-08-10 로컬 수정 (미배포)

- 오래된 NO_RESULT 991공고가 4,955 arm 행을 차지해 일일 limit 5,000을 거의
  독점했다. “다음 회차가 밀린 잔량을 처리한다”는 가정은 틀렸다.
- 채점 우선순위를 **개찰결과 보유 → 한 번도 확인하지 않음 → NO_RESULT 재시도**로
  고정하고, 세 큐의 arm 행/공고 수와 배치 전후 잔량을 노출한다.
- 모든 성능 집계는 `예정가격 / 등록시점 기초금액 = 0.94~1.06`인 최신 rev만
  사용하고 제외 수를 함께 보인다. 원장 행은 삭제·수정하지 않는다.
- G-A/G-B/G-C는 distinct 공고, 적격심사제 유효 표본, Wilson 95% CI로 자동
  판정한다. G-A 또는 유효 표본이 없으면 관리자 성능 화면을 잠근다.
- 월요일 21:00 누적 성적표와 2026 G2 재실행 경로를 추가했다. 자가보정 전략의
  자동 승격은 여전히 금지다(P5).
- 주간 성적표 생성 실패는 성공 결과로 삼키지 않는다. Celery가 최대 3회 재시도한
  뒤에도 실패하면 태스크를 `FAILURE`로 남겨 다음 주까지 조용히 누락되지 않게 한다.
- 2026 G2의 DB 조회 실패는 빈 표본 `NOT_READY`가 아니라 실행 실패다. 비정본 결과는
  source·method별 파일로 분리해 서로 덮어쓰지 않는다.

### 2026-08-11 독립 리뷰 — 등수 축 전제가 틀렸다 (운영 실측)

PR #62(Phase 2) 를 독립 리뷰하다 **등수 지표가 개찰조서와 다른 물건을 재고 있었다**는 것이
운영 데이터 대조에서 드러났다. 코드는 이렇게 단정하고 있었다 —
*"`opengRank` 와 같은 축이며 하한선 미달 참가자도 순위에 포함된다."* **사실과 반대였다.**

| 실측 (참가자 462,900행 전수) | 값 |
|---|---:|
| `rank` 결측 = 무효 투찰 | 220,491행 (**47.6%**) |
| 무효 포함 재계산 vs 저장된 `opengRank` 불일치 | **97.8%** |
| **유효 투찰만** 재계산 vs `opengRank` 불일치 | **0.054%** (130/242,409) |
| 등수가 채워진 채점 건 | 3,435 |
| **그중 무효(DROPOUT)** | **2,460 (71.6%)** — 아래 참조 |
| 유효 판정분(WIN+LOST) 평균 등수 → 실제 | 103.58 → **56.17** |
| 유효 판정분 1위 표시 vs 실제 1위 | 37 → **71** |

#### ③ 왜 빗나가는가 — `adjustment` 는 최적화가 식별하지 못하는 값이다

목적함수 J 는 `(adj, margin)` 을 **오직 곱** `(1+adj/100)×(하한율+margin)` 으로만
본다. 가격도(`simulate_params` optimizer.py:90-92) 임계비율도
(`risk_model.critical_ratio`) 그 곱의 함수다. 즉 **곱이 같은 조합은 J 가 같다** —
최적화에 adj 를 사정률로 끌어당길 힘이 없다. 유일하게 둘을 가르는 것은 이전
파라미터로부터의 거리 패널티 η 인데, 그건 데이터가 아니라 **직전 값**을 향한다.

운영 active 파라미터가 그 증거다. 세그먼트별 adj 는 **−1.0 ~ +0.9 로 1.9%p**
흩어져 있는데, 같은 파라미터의 유효 여유분(하한율 위 실제 쿠션)은
**0.489 ~ 0.951%p, 폭 0.463%p** 에 불과하다. 공격성은 거의 같은데 adj 만 제각각인
것이다. 그런데 실제 사정률 중앙값은 전 세그먼트 0.995~1.003 이다.

| 세그먼트 | adj | margin | 곱(하한율 89.745 기준) | 유효 여유분 |
|---|---:|---:|---:|---:|

밀고 차이를 margin 으로 흡수시키면 —

|---|---:|---:|---:|---:|

승패·무효가 **소수점 셋째 자리까지 한 건도 안 움직이는데** 사정률 오차만 17.6%
줄어든다. 우리가 4차 지표로 재던 것의 상당 부분은 시장이 아니라 **파라미터를
adj 와 margin 에 어떻게 쪼갰는가**였다. (참고: 이 표의 현행 행 13.861/5.281 은

**결론: §0.2 4차 지표는 지금 "우리 모델의 순수 신호"가 아니다.** 사정률 오차의

**부수 피해 — 이건 지표만의 문제가 아니다.** 최적화는 A값이 없는 세계에서
적합한다(`simulate_params` 는 `a_value` 를 보지 않는다). 그런데 운영 계산은
A값을 넣어 `(기초금액×(1+adj/100) − A)×(하한율+margin)/100 + A` 로 가격을 만든다.
이 식에서는 **곱이 같아도 adj/margin 배분이 다르면 가격이 달라진다.** 유효 표본의
**722/737(98%)이 A값을 갖고 있고**, 임의 배분이 실제로 옮기는 금액은 중앙값
5,730원(0.011%)·최대 534,330원(0.18%)이다. 작지만 0 이 아니고, 방향이 체계적이다.

#### ④ 오답노트(§6) 교차 — 태그 하나가 고장 나 있다

| 태그 | n | 비중 | MAE | 읽는 법 |
|---|---:|---:|---:|---|
| `기초금액_변경됨` | 724 | **98.2%** | 0.007142 | ⚠️ **상시 점등 = 신호 소실** |
| `기초금액_정정` | 40 | 5.4% | 0.007523 | 전체와 차이 없음 |
| `A값_결측` | 15 | 2.0% | 0.012849 | MAE 는 크지만 **oracle 도 0.012797** |
| `사정률_극단` | 2 | 0.3% | 0.045824 | 정의상 큼. 표본 없음 |
| `재공고건` | 1 | 0.1% | 0.009058 | 표본 없음 |

- **`기초금액_변경됨` 은 기초금액 전환 이후 의미를 잃었다.** 이 태그는
  `notice.basic_price` 와 스냅샷을 비교하는데, 스냅샷이 이제 `basis_amount` 라
  두 값은 **구조적으로 항상 ~10% 다르다**. 98% 점등은 공고가 바뀌었다는 뜻이
  아니라 비교 대상이 바뀌었다는 뜻이다. 비교 상대를 `basis_amount` 로 고쳐야 한다.
- **`A값_결측` 은 편향이 아니라 산포다.** MAE 가 전체의 1.8배지만 headroom 은
  +0.000052 로 사실상 0 — 그 공고들의 사정률 자체가 흩어져 있다(σ 0.0198 vs
  전체 0.0081). **A값을 채워도 사정률 예측은 안 좋아진다.** A값의 가치는
  가격 계산이지 사정률 추정이 아니다.
- 설계 §6 의 `A값_추정치`·`동가밀집`·`참여자_폭증`·`개찰지연` 은 **아직 코드에
  없다**. `하한율_테이블폴백`·`예가_비표준` 은 구현돼 있으나 현 표본에서 0건이다
  (하한율 전건 공고 명시, 예가 전건 15/4).

#### ⑤ 개선안

**R1 (핵심) — 사정률 추정을 자유 파라미터에서 분리한다.**
세그먼트별 `adjustment` 를 데이터에서 적합한 사정률 중심(중앙값, 얕은 세그먼트는
부모로 shrinkage — `risk_model` 과 같은 규율)에 **고정**하고, `margin` 하나만
최적화한다. 곱의 도달 범위가 줄지 않도록 margin 격자는 **커버리지 조건에서
유도**한다(상수로 박으면 고정값에 따라 한쪽이 조용히 잘린다).
얻는 것: ⓐ 4차 지표가 실제 사정률 예측의 오차가 된다 ⓑ 공격성이 `margin` 한
숫자로 읽힌다 ⓒ A값 가격 누수가 사라진다.

**R2 (표본 대기) — 예비가격 범위(±2%/±3%)를 축에 넣는다.** 유효 표본에서
±2% 공고(n=61)의 사정률은 중앙값 기준 MAE **0.004731**, ±3%(n=676)는 **0.006505**
다. 같은 예측을 쓰면서 이 차이를 못 쓰고 있다. 다만 ⓐ n=61 ⓑ 공사 공고
38,892건 중 범위 필드 보유가 **4,689건(12.1%, ±2 는 846건)** 이라 **지금 판단하지
않는다**. 커버리지가 오르면 재측정한다. ⛔ 판단 전에 `simulation_service` 의
±3% 하드코딩을 건드리지 말 것(§다음 주제 "예비가격 ±2%/±3% 판정" 과 같은 함정).

**R3 (즉시, 저비용) — 오답노트 수리.** `기초금액_변경됨` 의 비교 대상을
`basis_amount` 로 교체(현재 98% 오탐). §6 미구현 태그 4종은 구현하거나 설계에서
내린다 — 목록에만 있으면 다음 세션이 "이미 재고 있다"고 오판한다.

#### ⑥ 검증 — 기존 백테스트 경로(autocalibrate) + walk-forward

같은 목적함수·같은 제약·같은 상속 규칙을 쓰고 **탐색 축만** 바꿨다(원인 귀속을
위해 달라지는 것을 하나로 고정). 학습은 holdout 이전 연도 전체, 평가는 균등 가중.
2022~2025 는 정적 개찰 데이터(연도별 제외 0건), 2026 은 운영 `opening_results`
누적분을 `--include-db` 로 병합한 것이다 — **6,040건 중 719건(11.9%)이 기초금액
일관성에서 걸러져 5,321건**이 남았다(모의투찰 표본의 51.2% 제외와는 다른 모집단
이다. 이쪽은 개찰 API 의 `bssAmt` 라 애초에 기준이 맞는다).

| holdout | n | 방식 | win% | 무효% | 사정률 MAE | oracle 대비 |
|---|---:|---|---:|---:|---:|---:|
| 2022 | 821 | 현행 재적합 | 9.50 | 2.44 | 0.007240 | 1.256× |
| | | **개선안(R1)** | 9.13 | 3.04 | **0.005838** | **1.013×** |
| 2023 | 734 | 현행 재적합 | 9.13 | 2.73 | 0.007605 | 1.297× |
| | | **개선안(R1)** | 9.26 | 3.27 | **0.005918** | **1.009×** |
| 2024 | 695 | 현행 재적합 | 16.40 | 2.45 | 0.007420 | 1.312× |
| | | **개선안(R1)** | 18.70 | 2.88 | **0.005741** | **1.015×** |
| 2025 | 483 | 현행 재적합 | 27.54 | 5.59 | 0.007374 | 1.250× |
| | | **개선안(R1)** | 27.12 | 4.76 | **0.005982** | **1.014×** |
| **2026** | **5,321** | 현행 재적합 | 17.20 | 4.91 | 0.006906 | 1.152× |

- **사정률 오차가 oracle 바닥에 붙는다** — holdout 에서 바닥 대비 1.005~1.015배.
  바닥은 holdout 자신의 세그먼트 중앙값(사후)이므로, 그 안에 들어왔다는 것은
  **상수 예측으로 짜낼 수 있는 것이 남지 않았다**는 뜻이다.
- **승패는 사고파는 게 아니다.** 근거 둘: ⓐ 곱을 보존한 재배분은 win·무효를
  **정확히 0.000%p** 움직인다(위 ③ 표) — 재파라미터화 자체의 비용은 0 이다.
  ⓑ 축을 하나 줄여도 세그먼트별 도달 최선 J 가 그대로다(ΔJ −0.0027 ~ +0.0001,
  n≥100 세그먼트 5개). 따라서 walk-forward 의 win ±2.3%p·무효 ±0.8%p 출렁임은
  파라미터화가 아니라 **재적합 시 격자의 argmax 가 옮겨 간 것**이다(같은 J 근방의
  다른 점). 2026(n=5,321)에서는 win 17.20→17.14(CI 완전 겹침)·무효
  4.91→**4.42**(1차 지표가 오히려 개선).
- **과적합 없음.** 학습→holdout 의 MAE 낙폭이 개선안 −0.000115 ~ +0.000144 로
  현행(−0.000165 ~ +0.000335)보다 작다. 더 결정적으로 **고정된 adj 값이 학습
  연도를 바꿔도 거의 동일하다** — 4개 학습창 전부 −0.2 ~ 0.0 범위. 사정률 중심은
  연도 간 안정적인 상수에 가깝다.
- ⚠️ 2024·2025 의 win 급등(+6.9%p·+15.6%p)은 **두 방식 모두에서 같이** 나타난다.
  이건 `BENCHMARK_WIN_REACH.md` §3 의 소액수의견적 2024 레짐 변화이지 방법의
  성과가 아니다. ⚠️ 위 표의 "운영 active" 행은 2026 에서만 정당한 walk-forward
  비교다(v20260527 은 2021~2025 로 적합됐다) — 2022~2025 행에서는 자기 학습
  데이터를 평가하는 셈이라 참고용으로도 싣지 않았다.

#### ⑦ 교차검증 — 같은 과제를 독립 2회 돌렸다

같은 base 커밋(`a7423e4`)·같은 프롬프트로 **Claude 와 Codex 를 별도 워크트리에서
독립 실행**하고 결과를 대조했다. 세그먼트 분해는 사실이라 **둘이 같아야 정상**이고,
다르면 한쪽 쿼리가 틀렸다는 뜻이다.

**기준선 사정률 MAE 가 소수점 6자리까지 4/4 일치했다** — 2022 `0.006909` ·
2023 `0.007190` · 2024 `0.006955` · 2025 `0.007418`. 표본(4,848)과 기초금액
일관성 제외(0건)도 동일. 서로 다른 코드가 같은 원장에서 같은 값을 냈으므로
**위 ①~⑥ 의 사실 층은 신뢰해도 된다.**

개선안도 사실상 같은 값에 도달했다. 접근은 달랐다 — 이쪽은 J 안에서 곱을
보존한 채 `adjustment` 를 고정했고(R1), 저쪽은 사정비율 예측을 분리해 세그먼트
분포의 중앙값을 썼다(`risk_model.predict_reserved_ratio`). 그런데 holdout MAE 는
`0.005838` vs `0.005855`(2022) 처럼 **0.00002 안에서 갈린다.** 사정률 중심이
전 세그먼트 0.995~1.003 에 몰려 있어 두 경로가 같은 점으로 수렴한 것이다.

**합쳐야 나오는 결론 하나 — 쪼개도 얻는 게 없다.** 저쪽이 추가로 돌린 기관
부분풀링(shrinkage k=25)까지 세우면 pooled MAE 가 이렇게 늘어선다(n=2,733):

| 후보 | pooled MAE |
|---|---:|
| 거의 전역 상수 (R1, 학습창 전체에서 −0.2~0.0) | 0.005860 |
| 세그먼트별 중앙값 | 0.005876 |
| + 기관 부분풀링 | 0.005886 |

셋의 차이가 0.00001~0.00003 — **서로 구분되지 않는다.** ⑥ 이 "상수 예측으로
짜낼 것이 남지 않았다"였다면, 여기서 한 칸 더 나아간다: **금액대·입찰방법 위에
기관을 더 얹어도 신호가 없다.** 그래서 `ratio_error.py` 의 후보 선택은 MAE
최소가 아니라 **동점(≤`TIE_MARGIN`)이면 덜 쪼갠 쪽**을 고른다 — 순수 최소로
고르면 연도 하나 바뀔 때마다 순위가 뒤집히는 노이즈가 기관 차원을 채택시킨다.

**교차검증이 잡은 결함 3건**(전부 이번에 수정):

| 결함 | 성격 |
|---|---|
| 기준선이 walk-forward 규칙 밖 — 2021~2025 로 적합된 저장본을 2022 holdout 에 사용 | 방향은 안전(기준선에 유리)하나 **delta 가 개선폭의 하한**이라 성과로 인용 불가. 페이로드에 `baseline_is_walk_forward: false` 를 박고 manifest 를 정정 |
| 후보 선택 docstring("증거가 없으면 단순한 쪽")과 코드(`min(mae)`)가 반대 | 실측이 우연히 단순한 쪽이라 드러나지 않고 있었다 |
| 세그먼트 리포트 테스트가 단독 실행만 통과 | 같은 셀에 행이 누적돼 최소 표본(n<20) 조건이 뒤집힘 — 전용 기관명으로 격리 |

⚠️ **셋 다 "돌려보고 대조해야" 나왔다.** 특히 첫 번째는 계약 파일(manifest)이
`train_rule` 을 선언해 놓고 기준선은 그 규칙을 안 지킨 경우다 — **선언과 실행이
어긋나도 테스트는 green 이었다**(§7 함정 목록의 "테스트 통과 ≠ 작동"과 같은 종류).

### 2026-08-14 — R1 적용: 파라미터화를 `ratio_pinned_v2` 로 전환

위 §9(08-13) 의 R1 을 실제로 넣었다. `adjustment` 를 데이터에서 적합한 사정률
중심(중앙값·부모 shrinkage)에 **고정**하고 `margin` 하나만 최적화한다.

**⚠️ 승격 가드가 이 전환을 막는다 — 그래서 루프 밖에서 1회 실행한다.**
`guard.MAX_PARAM_JUMP = 1.0` 은 같은 축 위의 점진 재보정을 감시하라고 둔
값인데, 파라미터화 전환은 축 자체가 바뀌는 일이라 `adjustment` 가 한 번에 최대
1.0 옮겨간다(적격심사제/small −1.0 → −0.0). 주간 재보정에 맡기면 후보가 거부돼
active 는 옛 축에 머문다. **가드에 우회 경로를 뚫지 않았다** — 뚫으면 다음에
누군가 그 문으로 들어온다. 대신 전환만 `scripts/migrate_strategy_parametrization.py`
로 사람이 1회 실행한다. 전환 뒤엔 새 축이 기준선이라 이후 재보정은 `margin` 만
움직여 가드 안에 들어온다.

**전환은 곱을 보존한다 — 다만 반올림 방향이 곧 위험 방향이다.** 격자가 0.1%p 라
곱이 정확히 같을 수 없는데, **곱이 줄면 투찰가가 낙찰하한선에 가까워져 무효
위험이 커진다**(무효율 = §0.2 1차 지표). 첫 구현은 단순 반올림이라 이탈이
−0.0408 ~ +0.08 로 갈렸고 **`DEFAULT/medium` 이 음수쪽**이었다 — 그게 Pro+
`/smart_bid/recommend` 가 쓰는 바로 그 세그먼트다. 잔차를 **항상 안전한 쪽으로
올림**하도록 고쳐 이탈을 전량 양수로 만들었다(현재 `+0.0000 ~ +0.0907` — 아래
③을 고치기 전에는 최대 `+0.4214` 였다).

**`margin` 은 0.0 미만이 될 수 없다.** 사정률 중심이 크게 잡힌 세그먼트에서 곱을
맞추려다 **−0.4 가 나왔다**(실시설계기술제안입찰/xxlarge — 하한율 아래라 그
세그먼트 전건이 무효가 될 뻔했다). 그 경우 곱 보존을 포기하고 0.0 으로 막는다.
방어는 남겨 뒀지만, 아래 ③을 고친 뒤로는 실제로 발동하지 않는다.

**③ 얕은 표본의 부모 중앙값이 예측을 지배하고 있었다 (미리보기가 잡았다).**
`실시설계기술제안입찰/xxlarge` 의 고정 adjustment 가 **+1.3**(사정률 중심 1.0133)
으로 나왔는데, 사정률은 정의상 1.0 근처다(실측 전 세그먼트 0.995~1.003).
파고 보니 원인이 둘 겹쳐 있었다 — ⓐ `_by_method` 생성에 **최소 표본 조건이 없다**
(`if vals:` 뿐)라 입찰방법 전체가 **n=2** 인 것도 부모가 되고 ⓑ 희소 세그먼트는
`risk_model.py:179` 에서 부모의 분위수를 **통째로** 물려받는다(`mu` 는 shrinkage
하는데 `quantiles` 는 대체다). 표본이 충분한 방법은 전부 −0.1 로 수렴한다
(적격심사제 n=1,117 · 소액수의견적 n=3,671 · 전역 0.99872) — **튀는 건 신호가
아니라 노이즈였다.**

⚠️ **옛 2축에서는 이 결함이 드러날 수 없었다.** `adjustment` 가 어차피 식별되지
않는 값이었으니 그게 노이즈든 아니든 아무도 읽지 않았다. R1 이 그 값을 **예측으로
승격**시키는 순간 표본 부족이 그대로 실사용자 가격에 실린다. 파라미터를 의미
있는 값으로 바꾸면, 그 값을 만들던 경로의 품질 문제도 같이 승격된다.

수정 = `predict_reserved_ratio` 가 `get_segment` 를 믿지 않고 **전역 → 방법 →
세그먼트** 순으로 직접 부분풀링한다(각 층 `n/(n+SHRINKAGE_K)`, 세그먼트 층은
`source=="own"` 일 때만 — 희소 세그먼트의 분위수는 이미 부모 것이라 다시 섞으면
같은 값을 두 번 센다). 결과: adj +1.3 → **−0.0**, 수의시담 −0.6 → −0.2,
곱 이탈 `+0.0007~+0.4214` → **`+0.0000~+0.0907`**, margin 클램프 **해소**.

| | 값 |
|---|---|
| 실행 | `python scripts/migrate_strategy_parametrization.py [--commit]` (기본은 미리보기) |
| 순서 | **배포 직후·주간 재보정(월 04:00) 이전.** 뒤집히면 한 사이클 헛돈다(무해) |
| 영향 | Pro+ `/smart_bid/recommend`(DEFAULT 세그먼트) · 이후 등록되는 모의투찰 arm |
| 롤백 | `store.rollback('<이전 version_id>')` |

**분석 분리(§3)** — `StrategyVersion.parametrization` 이 축을 밝힌다(`product_v1`
= 옛 2축, 기본값이라 필드 없는 옛 파일도 옳게 읽힌다 / `ratio_pinned_v2` = 신규).
arm 은 `strategy_version` 을 이미 스냅샷으로 남기므로 전환 시점에 자동으로 갈린다.
⛔ **두 리비전의 `adjustment` 를 같은 축에서 비교하지 말 것** — 옛 값은 사정률
예측이 아니라 margin 과의 임의 배분이다.

**되돌림 방지** — 회귀 4종을 주입해 테스트가 각각 잡는 것을 확인했다: ⓐ adj 탐색
부활 ⓑ margin 격자 상한 상수화(공격적 후보가 조용히 잘린다) ⓒ 안전 방향 올림을
반올림으로 복귀 ⓓ 얕은 표본 shrinkage 해제. 넷 다 잡힌다.

#### ⑧ 남은 것 (착수 전)

- **적용은 하지 않았다** — §P5 대로 제안·검증까지다. R1 을 넣으려면
  `optimizer.optimize_segment` 의 탐색 축을 바꿔야 하고, 그건 자가보정 루프의
  파라미터 의미가 바뀌는 변경이라 **사용자 결정 사항**이다.
- **저장된 파라미터의 하위 호환** — 기존 버전의 `adjustment` 는 사정률이 아니다.
  R1 적용 시 과거 버전과 새 버전의 `adjustment` 를 같은 축에서 비교하면 안 된다
  (전략 버전에 파라미터화 리비전을 함께 박아야 한다).
- **모의투찰 arm 재등록은 하지 않는다** — 등록 행은 불변(§0.5-3). R1 을 적용하면
  그 시점 이후 등록분부터 다른 파라미터화가 되므로 §3 규칙대로 **버전을 올리고
  분석에서 분리**한다.
- 4차 지표를 화면·주간 리포트에서 "모델 정확도"로 읽지 말 것 — R1 적용 전까지는
  파라미터화 부산물이 섞여 있다.

### 2026-08-17 — 가상 등수축 오염과 최종 참가자 스냅샷 수습

재현은 단순하다. 진행 중 응답이 `A(1), B(2), C(3)`이고 다음 응답이

1. 낙찰자 미확정 응답은 기존처럼 merge한다. 조회 창 전체가 성공한 뒤에만 저장하는
